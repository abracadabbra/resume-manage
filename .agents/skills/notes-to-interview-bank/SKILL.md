# Skill: notes-to-interview-bank

从原始小红书笔记（XLS 列表 + 截图文件夹）到结构化面试题库的完整加工流水线。

## 输入

| 来源 | 类型 | 说明 |
|---|---|---|
| `笔记列表.xls` | 文件 | 小红书笔记元数据（标题、正文、标签、链接、发布时间等） |
| `笔记/` | 目录 | 每条笔记一个子目录，内含截图（webp/png/jpg）和可选的标题+内容 TXT |
| API Key | 环境/输入 | OpenAI 或 Anthropic 协议的 LLM API |

## 输出

`笔记列表_含OCR.xlsx`，包含：

- **原始列**：全部保留
- **本地图片数量 / 本地图片文件 / OCR识别文本**：Phase 1 追加
- **正文+OCR整合**（col 26）：正文 + OCR 拼接
- **整合内容(v2)**（col 28）：LLM 结构化后的 `## 面试题 / ### 领域 / - 问题` 格式
- **面试题库 Sheet**：拍平后的行式数据，每行一道题

## 处理流程

```
Phase 1 — OCR + 字段合并
  scan_and_ocr.py ─→ 笔记汇总_含OCR.xlsx
  merge_to_xls.py  ─→ 笔记列表_含OCR.xlsx（含 OCR 列）
  追加正文+OCR整合列 ─→ col 26

Phase 2 — 逐条 LLM 结构化（核心）
  generate_v2.py ─→ 写回整合内容(v2) 到 col 28
  规则：一条笔记一次 API 调用，不批量

Phase 3 — 题库 Sheet 生成
  generate_bank.py ─→ 解析 v2 → 面试题库 Sheet
```

---

## Phase 1：OCR + 字段合并

### 1.1 扫描图片 + OCR

使用 `scan_and_ocr.py`（位于输入目录）。对 `笔记/` 下每个子目录中的图片执行 macOS Vision OCR：

```bash
python3 scan_and_ocr.py
```

输出：`笔记汇总_含OCR.xlsx`（含 笔记汇总 + 图片OCR详情 两个 Sheet）

### 1.2 合并到 XLS

使用 `merge_to_xls.py`：

```bash
python3 merge_to_xls.py
```

将 XLS 的元数据与 OCR 结果按标题⫻文件夹名匹配合并，输出 `笔记列表_含OCR.xlsx`。

匹配策略：精确匹配 → 已知映射（特殊字符差异） → 规范化匹配（去空格/斜杠/竖线后比较）

### 1.3 生成正文+OCR整合列

合并公式：`{正文} + "\n\n---\n\n" + {OCR识别文本}`

若两者皆为空，该行为空。写入 col 26。

---

## Phase 2：逐条 LLM 结构化（核心）

### 关键原则

**必须一条笔记一次 API 调用。** 批量调用会导致 LLM 为节省上下文而截断长行，这是原始 v2 质量问题的根因。

### 前置条件

- Python 环境：`openpyxl` 已安装
- API 信息：地址、Key、模型名（定义在脚本顶部常量中）

### 执行

```bash
python3 generate_v2.py
```

### Prompt 模板

```
## 角色
你是一名面试题库整理专家。

## 任务
下面是一条面经笔记的原始内容。请提取所有面试题，按技术领域分组，输出为以下格式：

## 面试题
### Java
- [完整的问题描述]
- [完整的问题描述]
### MySQL
- [完整的问题描述]
...

## 要求
1. 问题表述务必完整，不能截断
2. 保留 SQL 代码、算法题描述等细节
3. 根据内容判断技术领域（Java/MySQL/Redis/MQ/算法/系统设计/项目/网络/操作系统等）
4. 如果内容不含任何面试题（如招聘广告、闲聊、行业讨论），只输出"（该笔记为行业讨论帖）"
5. 只输出整理后的内容，不要额外解释

## 原始内容
{content}
```

### 处理规则

- 空源 → 写 `（该笔记为空）`
- API 失败 → 重试 3 次，间隔递增（5s / 10s / 15s）
- 每 10 条自动保存 Excel
- SSE 流式响应：收集 `choices[0].delta.content`
- 非技术帖标记：原有 `（该笔记为行业讨论帖）` 续用

### API 协议配置

脚本同时支持两种协议，`PROTOCOL` 常量切换：

- **OpenAI 协议**（默认）：`POST /v1/chat/completions`，`Authorization: Bearer`
- **Anthropic 协议**：`POST /v1/messages`，`x-api-key` + `anthropic-version`

## Phase 3：题库 Sheet 生成

解析 col 28 的 `## → ### → -` 三级结构，拍平为 面试题库 Sheet。

```bash
python3 generate_bank.py
```

### 解析逻辑

| 行开头 | 含义 |
|---|---|
| `## ` | 轮次名（面试题 / 一面 / 二面 / 补充问题） |
| `### ` | 技术领域（Java / MySQL / Redis / 算法 / 系统设计 / …） |
| `- ` | 题目行 |
| `（该笔记为行业讨论帖）` | 跳过 |
| 空行 | 跳过 |

### 列映射

| 面试题库列 | 来源 |
|---|---|
| 笔记ID | 原表 col 1 |
| 标题 | 原表 col 5 |
| 公司 | 从标题匹配（滴滴/字节/腾讯/美团/快手等） |
| 岗位 | 从标题+内容匹配（Java/前端/算法/数据/客户端等） |
| 轮次 | `## ` 内容 |
| 技术领域 | `### ` 内容 |
| 题目 | `- ` 内容（含 SQL 续行合并） |
| 链接 | 原表 col 17 |
| 发布时间 | 原表 col 15 |

### SQL 续行合并

若 `- ` 行后续的 `- ` 行以 `.` 开头或匹配 SQL 关键字开头（`create`/`select`/`insert`/`from`/`where` 等），合并到上一题。仅在 SQL 场景下合并，不合并中文续行。

---

## 关键决策记录

| 决策 | 原因 |
|---|---|
| 一条笔记一次 API 调用 | 批量调用时 LLM 截断长行，导致 `有没有更`、`说出核` 等碎片 |
| 源用正文+OCR整合而非纯正文 | OCR 补充截图中的算法题、SQL 代码、面经补充信息 |
| 仅 SQL 场景做续行合并 | 中文文本碎片合并会误将独立问题拼接（原 bug 根因） |
| 正文+OCR整合作为独立列 | 保留原始拼接数据，方便排查 LLM 结构化异常 |
| MiniMax-M3 已验证可用 | 响应快、不截断、支持完整 4096 token 输出 |
